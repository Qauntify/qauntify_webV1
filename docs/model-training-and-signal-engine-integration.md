# Model Training and Signal Engine Integration

## 1. Purpose

This document defines how Quantify should train, validate, deploy, and monitor machine-learning models that work with the existing signal engine.

The model's primary job is **not** to predict the next market price. Its primary job is to estimate whether a candidate setup generated by the engine has positive expected value after its stop-loss, staged take-profit rules, expiry rules, spread, fees, and slippage are considered.

The recommended system keeps the existing rule-based strategies as candidate generators and adds a calibrated outcome model as a decision-support layer. The LLM remains useful for qualitative review and explanations, but it should not be the only numeric trade-selection mechanism.

The target architecture is:

```text
Market candles and context
          |
          v
Technical indicators and strategy detectors
          |
          v
Candidate setup (long/short, entry, stop, TP1/TP2/TP3)
          |
          v
ML outcome model -> calibrated outcome probabilities -> expected R
          |
          v
Risk/quality gate
          |
          v
LLM qualitative review and rationale
          |
          v
Store, alert, and track the signal
          |
          v
Resolved outcome -> training dataset -> retraining
```

## 2. Current Signal Engine Context

Quantify currently:

- Scans `BTCUSD`, `ETHUSD`, `XAUUSD`, and `GBPUSD`.
- Operates on multiple streams, including 5-minute super-scalp, 15-minute scalp, and 1-hour swing sessions.
- Generates candidates with rule-based strategies such as `ema_cross`, `ict_smc`, `ce_lwma`, `ict_fvg`, and `sr_zone`.
- Calculates entry, stop-loss, and staged targets at TP1, TP2, and TP3.
- Uses higher-timeframe trend confirmation for selected sessions.
- Uses an LLM to confirm or reject candidates and provide confidence and rationale.
- Stores confirmed signals and tracks them through `open`, `tp1_hit`, `tp2_hit`, `tp3_hit`, `sl_hit`, or `expired` states.
- Calculates realized R and calibration summaries from resolved signals.
- Contains existing XAUUSD LSTM artifacts for M1, M5, M15, M30, and H1.

The current engine provides a strong deterministic foundation. Machine learning should rank and filter candidates produced by this foundation rather than replace the detectors immediately.

## 3. Training Objective

### 3.1 Recommended objective

Train the model to predict the eventual outcome of every candidate setup. A useful initial multiclass label is:

| Label | Meaning | Example realized R |
|---|---|---:|
| `sl_before_tp1` | Stop-loss occurs before TP1 | `-1R` |
| `tp1_then_sl` | TP1 is banked, then the remaining position stops | `0R` |
| `tp2_then_sl` | TP1 and TP2 are banked, then the remainder stops | `+1R` |
| `tp3_hit` | Final target is reached | `+3R` |
| `expired` | Neither final target nor stop resolves before expiry | Actual marked-to-market R |

The example R values must match the engine's exact position-sizing and scale-out rules. If execution policy changes, the label calculation must change with it.

### 3.2 Expected-R decision

The model should return probabilities for every outcome. The engine can convert them into expected R:

```text
expected_R =
    P(sl_before_tp1) * -1
  + P(tp1_then_sl)   *  0
  + P(tp2_then_sl)   *  1
  + P(tp3_hit)       *  3
  + P(expired)       * expected_expiry_R
  - estimated_cost_R
```

The engine should accept a candidate only if expected R exceeds a configurable threshold and all existing risk controls pass.

An initial threshold might be `expected_R > 0.10`, but this value must be chosen from walk-forward validation. It must not be guessed or optimized on the final test period.

### 3.3 Optional secondary objectives

After the multiclass system is stable, additional models can estimate:

- Probability that TP1 occurs before stop-loss.
- Probability that TP2 occurs after TP1.
- Probability that TP3 occurs after TP2.
- Expected realized R directly.
- Bars or elapsed time until TP/SL/expiry.
- Maximum favorable and adverse excursion.
- Market regime or volatility state.

The conditional TP models are useful because they respect the ordered TP ladder. They should be challengers to the simpler multiclass design, not the first implementation.

## 4. Data Collection

### 4.1 Record every candidate

The most important requirement is to record **every strategy candidate**, including candidates rejected by the LLM or ML gate.

Training only on stored live signals creates selection bias because the dataset excludes rejected trades and cannot teach the model whether those rejections were correct. Every candidate must be paper-tracked under the same entry, stop, TP, and expiry logic used for live signals.

### 4.2 Candidate snapshot

At candidate creation time, store an immutable snapshot containing:

```text
candidate_id
created_at
symbol
timeframe
session
strategy
direction
entry
stop_loss
take_profit_1
take_profit_2
take_profit_3
feature_schema_version
features
llm_model
llm_verdict
llm_confidence
llm_rationale
ml_model_version
ml_probabilities
ml_expected_r
engine_decision
engine_decision_reason
```

After resolution, append:

```text
status
tp1_hit_at
tp2_hit_at
tp3_hit_at
closed_at
exit_price
realized_r
maximum_favorable_excursion_r
maximum_adverse_excursion_r
bars_to_resolution
estimated_fees
estimated_spread
estimated_slippage
```

Do not overwrite the original feature snapshot when indicators or settings later change.

### 4.3 Suggested database tables

Use a separate training table rather than overloading the live `signals` table:

```text
model_candidates
  - immutable candidate and feature snapshot
  - decisions from rules, ML, and LLM
  - model and schema versions

model_candidate_outcomes
  - resolved market path and labels
  - execution costs and realized R

model_registry
  - model name and version
  - training window
  - feature schema version
  - validation metrics
  - artifact location and checksum
  - lifecycle status: candidate/shadow/active/retired
```

Keep training data access private. It can contain strategy logic, model decisions, and operational metadata that should not be publicly readable.

## 5. Features

### 5.1 Core feature groups

Each training row represents one candidate, not one arbitrary candle.

#### Identity and context

- Symbol
- Timeframe
- Session (`super_scalp`, `scalp`, or `swing`)
- Strategy
- Direction
- Hour of day
- Day of week
- Trading-session indicators such as Asia, London, and New York

#### Trend and momentum

- RSI
- ADX and directional components, if available
- MACD histogram and recent change
- EMA 9/21 distance and slope
- Higher-timeframe trend
- Multi-timeframe trend agreement

#### Volatility and candle structure

- ATR and ATR percentile
- Realized volatility over multiple windows
- Candle body/range ratio
- Upper- and lower-wick ratios
- Recent range expansion or contraction
- Gap or fair-value-gap size and age

#### Strategy-specific information

- Support/resistance zone strength, touches, width, and distance
- ICT/FVG direction, size, displacement, and mitigation status
- EMA crossover age and separation
- Chandelier Exit/LWMA relationship
- Detector-specific quality flags

#### Trade geometry

- Stop distance in ATR units
- TP distances in ATR units
- Risk/reward ratios
- Entry distance from recent high/low
- Entry distance from support/resistance

#### Market and execution context

- Relative volume
- Spread estimate
- Expected slippage
- Scheduled high-impact news proximity
- Market volatility regime
- Recent gap or weekend-open indicator

#### Historical context

- Recent strategy performance using only information available before the candidate
- Recent symbol/timeframe performance
- Consecutive wins/losses, carefully windowed
- Recent calibration error

### 5.2 Existing LSTM outputs

The existing XAUUSD LSTMs can be retained as feature generators. Useful derived features include:

- Predicted return rather than raw predicted price
- Predicted direction
- Prediction magnitude normalized by ATR
- Agreement across M5/M15/H1 models
- Recent rolling prediction error
- Whether LSTM direction agrees with the rule-based candidate

An LSTM should not directly approve trades until it proves incremental value over models trained on candidate outcomes.

### 5.3 Feature normalization

Avoid raw price-level features where a normalized value is possible. For example:

```text
(close - ema21) / ATR
(ema9 - ema21) / ATR
abs(entry - stop_loss) / ATR
volume / rolling_median_volume
```

Normalized features transfer more reliably across symbols and market regimes.

### 5.4 Leakage controls

Every feature must be computable at the candidate timestamp. Never include:

- Future candles
- Final signal status
- Future TP or stop timestamps
- Post-candidate news
- Revised economic values that were unavailable at prediction time
- Calibration summaries containing the current candidate or later candidates
- Indicators calculated with an unclosed candle when live inference uses only closed candles

Fit scalers, encoders, imputers, feature selectors, and calibrators only on the training portion of each walk-forward split.

## 6. Recommended Models

### 6.1 Baseline: logistic regression

Build a logistic regression baseline for `P(TP1 before SL)`.

Advantages:

- Easy to debug and interpret
- Fast to train
- Produces a useful performance floor
- Helps expose leakage and broken features
- Provides a reliable fallback

The production candidate model should demonstrate meaningful improvement over this baseline after costs.

### 6.2 Primary model: CatBoost

CatBoost is the recommended first production candidate because the candidate dataset combines numeric indicators with categorical fields such as symbol, timeframe, strategy, session, and direction.

Train a multiclass classifier that emits the five outcome probabilities. Use class weights if rare TP3 outcomes are underrepresented, but validate that weighting does not destroy probability calibration.

Key advantages:

- Native categorical-feature handling
- Strong performance on small-to-medium tabular datasets
- Handles nonlinear feature interactions
- Minimal preprocessing
- Feature-importance and SHAP tooling

### 6.3 Challenger model: LightGBM

Train LightGBM on the same features, splits, and labels. It is a strong challenger when the dataset grows and training speed matters.

Do not choose between CatBoost and LightGBM based on headline accuracy. Select the model using out-of-sample expected R, drawdown, calibration, stability across folds, and live shadow results.

### 6.4 Optional XGBoost models

XGBoost can be used as another tabular challenger. Its survival objectives may later help model time to TP or stop while handling unresolved/censored candidates.

This is an advanced phase. A correct, calibrated multiclass model should come first.

### 6.5 Deep sequence models

LSTM, GRU, Temporal Convolutional Networks, and time-series Transformers should be considered only when Quantify has:

- A large and clean historical dataset
- Stable feature and label definitions
- Correct walk-forward evaluation
- Evidence that candle sequences add value beyond engineered features
- Sufficient compute and model-monitoring capacity

Deep models can process sequences, but they introduce higher overfitting risk, slower retraining, more complicated inference, and more difficult explanations. They should compete against CatBoost in a controlled experiment rather than replace it by assumption.

### 6.6 Role of the LLM

The LLM should remain responsible for:

- Summarizing news and market context
- Identifying qualitative risks not present in numeric features
- Producing a human-readable rationale
- Returning `confirm`, `caution`, or `reject` with a structured response

The LLM should not be treated as a statistically calibrated probability model. Store its verdict and confidence separately from the ML model's calibrated probabilities.

Initially, a candidate should have to pass both the numeric expected-R gate and the existing LLM/risk gate. Later, an experiment can determine whether the LLM improves realized performance after the ML score is known.

## 7. Training Workflow

### 7.1 Dataset construction

1. Read immutable candidate snapshots.
2. Join each candidate to its resolved outcome.
3. Exclude unresolved records from ordinary supervised training, or treat them explicitly as censored data in a survival model.
4. Recalculate labels using one versioned outcome-label function.
5. Validate feature ranges, missingness, timestamps, and duplicate candidate IDs.
6. Sort strictly by candidate time.
7. Produce a versioned dataset manifest with row count, time range, schema version, and checksum.

### 7.2 Time-based splitting

Never use a random split. Use chronological walk-forward evaluation:

```text
Fold 1: train Jan-Mar -> validate Apr
Fold 2: train Jan-Apr -> validate May
Fold 3: train Jan-May -> validate Jun
Final untouched test: Jul
```

Add a gap between train and validation periods at least as long as the maximum signal lifetime. This prevents a trade opened in the training period from resolving inside the validation period and leaking its future path.

When candidates overlap heavily, use purging or embargo logic so near-identical market paths do not appear on both sides of a split.

### 7.3 Hyperparameter tuning

Tune only inside the training window. Keep the search small initially:

- Tree depth
- Learning rate
- Number of iterations
- L2 regularization
- Minimum samples per leaf
- Feature subsampling
- Class weights

Optimize for a combination of log loss, calibration, and trading utility. Do not optimize only for accuracy because a model can achieve high accuracy by over-predicting the most common outcome.

### 7.4 Probability calibration

Calibrate predicted probabilities on data not used to fit the underlying model. Compare:

- Sigmoid/Platt scaling
- Isotonic regression when sufficient data exists
- Temperature scaling for multiclass outputs

Store the calibrator with the model artifact. Inference must always apply the matching calibrator before expected R is calculated.

### 7.5 Evaluation metrics

#### Statistical metrics

- Multiclass log loss
- Brier score
- Calibration error and reliability plots
- Per-class precision and recall
- Confusion matrix
- PR-AUC for rare positive outcomes

#### Trading metrics

- Average realized R per accepted candidate
- Total realized R
- Profit factor
- Maximum drawdown
- Win rate
- TP1, TP2, and TP3 hit rates
- Acceptance rate and trades per week
- Performance after spread, fees, and slippage
- Performance by symbol, timeframe, strategy, session, and market regime

#### Stability metrics

- Variation across walk-forward folds
- Performance degradation by month
- Sensitivity to threshold changes
- Feature drift
- Probability calibration by subgroup

The selected model should be profitable and stable across several periods. A single exceptional fold is not sufficient.

## 8. Signal Engine Integration

### 8.1 Inference boundary

Keep offline training and production inference in separate packages while using
one canonical feature builder:

```text
signals/ml/
  feature_schema.py
  features.py
  predictor.py
  expected_r.py
  registry.py

ml/
  training/
  labels/
  evaluation/
  notebooks/
```

`signals/ml/` must remain production-only. Training code imports the canonical
feature implementation from `signals/ml/features.py`; the signal engine never
imports or executes the offline `ml/training/` package.

The inference interface should be small and deterministic:

```python
prediction = predictor.score_candidate(
    setup=setup,
    candles=candles,
    indicators=indicators,
    session=session,
    context=context,
)
```

Recommended output:

```python
{
    "model_name": "candidate_outcome_catboost",
    "model_version": "2026-07-23.1",
    "feature_schema_version": "v1",
    "probabilities": {
        "sl_before_tp1": 0.24,
        "tp1_then_sl": 0.18,
        "tp2_then_sl": 0.16,
        "tp3_hit": 0.34,
        "expired": 0.08,
    },
    "expected_r": 0.82,
    "accepted": True,
    "reason": "expected_r_above_threshold",
}
```

### 8.2 Engine decision sequence

Recommended order:

1. Fetch and validate closed candles.
2. Calculate indicators.
3. Run the configured strategy detector.
4. If no setup exists, record a normal `no_setup` event.
5. Create and persist the candidate feature snapshot.
6. Score the candidate with the active ML model.
7. Apply expected-R, confidence, freshness, and risk thresholds.
8. Run the LLM qualitative review if the ML/risk gate passes, or run it in shadow mode for research.
9. Store and alert accepted signals.
10. Paper-track rejected candidates as well as accepted signals.
11. Resolve outcomes through the same chronological candle logic.

### 8.3 Failure behavior

ML integration must fail safely:

- If the model artifact cannot load, follow a configurable fallback: reject, use rules+LLM, or use the previous healthy model.
- If the feature schema does not match, do not silently fill unknown fields.
- If required features are missing, return a structured abstention.
- If inference exceeds a timeout, continue according to the configured fallback.
- Log failures without including secrets or private market credentials.

For initial deployment, `rules + LLM` is the safest fallback because it preserves current behavior.

### 8.4 Configuration

Suggested settings:

```text
ML_ENABLED
ML_MODE=off|shadow|advisory|enforced
ML_MODEL_NAME
ML_MODEL_VERSION
ML_MIN_EXPECTED_R
ML_MIN_TP1_PROBABILITY
ML_MAX_INFERENCE_MS
ML_FALLBACK=rules_llm|reject|previous_model
```

Allow thresholds by strategy and timeframe because a 5-minute scalp and a 1-hour swing have different cost structures, sample sizes, and payoff distributions.

## 9. Deployment Strategy

### Phase 1: Offline baseline

- Implement candidate and outcome storage.
- Backfill historical candidates by replaying detectors on historical candles.
- Train logistic regression, CatBoost, and LightGBM.
- Evaluate with walk-forward splits.
- Do not affect live decisions.

### Phase 2: Shadow mode

- Score every live candidate.
- Store predictions and expected R.
- Do not use ML to accept or reject trades.
- Compare predicted probabilities with resolved outcomes.
- Measure latency, missing features, drift, and calibration.

### Phase 3: Advisory mode

- Display model probabilities, expected R, and model version in the admin/training UI.
- Let existing rules and LLM remain authoritative.
- Review disagreements between ML, LLM, and realized outcomes.

### Phase 4: Limited enforcement

- Enable the ML gate for one strategy and timeframe with enough data.
- Use conservative thresholds.
- Keep a rollback switch.
- Compare against a shadow control group if operationally possible.

### Phase 5: Full monitored integration

- Expand only when out-of-sample and live results remain stable.
- Retrain on a controlled schedule.
- Require model-registry approval before activation.
- Keep the previous artifact available for immediate rollback.

## 10. Monitoring and Retraining

### 10.1 Live monitoring

Monitor:

- Candidate volume
- Acceptance rate
- Expected-R distribution
- Actual realized R
- Probability calibration
- Feature missingness
- Feature and prediction drift
- Inference errors and latency
- Results by symbol, timeframe, strategy, and regime
- ML/LLM disagreement rate

### 10.2 Retraining triggers

Retrain on a schedule only when enough new resolved candidates exist. Also consider retraining when:

- Calibration deteriorates materially
- Feature distributions drift
- Strategy logic changes
- TP/SL/expiry or scale-out rules change
- A new symbol or timeframe is introduced
- Live expected R falls below an agreed threshold

Every strategy-logic or label-policy change creates a new data regime. Record these versions and avoid mixing incompatible outcomes without explicit migration logic.

### 10.3 Model promotion rules

A new model should become active only if it:

- Beats the current model and logistic baseline on untouched time periods
- Improves or preserves expected R after costs
- Does not introduce unacceptable drawdown
- Is reasonably calibrated
- Performs consistently across important subgroups
- Passes artifact, schema, and inference integration tests
- Completes a shadow period without operational failures

## 11. Training and Admin UI

The model-training section should display:

- Dataset coverage and number of resolved candidates
- Candidate count by symbol, timeframe, strategy, and outcome
- Current feature-schema version
- Active model and previous model
- Training window and last trained time
- Walk-forward metrics
- Calibration plot
- Confusion matrix
- Feature importance/SHAP summary
- Expected-R threshold analysis
- Shadow versus active performance
- Drift warnings
- Retraining status and logs
- Promotion and rollback controls with audit history

Training should run as a controlled backend job or CI workflow. The UI should trigger or monitor the job, not train a model inside a browser request.

## 12. Testing Requirements

Add automated tests for:

- Feature calculation from fixed candle fixtures
- No use of future candles
- Identical offline and live feature output
- Outcome-label calculation for every TP/SL sequence
- Expected-R calculation
- Probability sums and valid ranges
- Feature-schema mismatch behavior
- Missing-feature abstention
- Model loading and fallback behavior
- Deterministic inference from a fixed artifact
- Shadow mode never affecting live decisions
- Enforced mode applying thresholds correctly
- Model-version and prediction logging

Include an end-to-end test that replays a candidate from candles through detector, feature generation, model scoring, decision, and outcome recording.

## 13. Security and Reproducibility

- Never pickle or load model artifacts from untrusted sources.
- Store artifacts in a private, versioned location.
- Record a checksum for every artifact.
- Pin training dependencies.
- Store the source commit, dataset manifest, random seed, parameters, metrics, and feature schema with every model.
- Do not store API keys or database secrets inside notebooks or artifacts.
- Separate training permissions from model-promotion permissions.
- Keep an audit record of who activated or rolled back a model.

## 14. Recommended First Implementation

The first practical release should contain:

1. A database record for every candidate, accepted or rejected.
2. A shared feature builder used by training and live inference.
3. A versioned outcome-label function based on existing TP1/TP2/TP3 tracking.
4. A logistic-regression baseline.
5. A calibrated CatBoost multiclass model.
6. Walk-forward validation with a maximum-signal-lifetime gap.
7. Expected-R scoring after estimated costs.
8. Shadow-mode integration with no effect on current live signals.
9. Monitoring of calibration, realized R, drift, and ML/LLM disagreement.
10. A controlled path from shadow to advisory and then limited enforcement.

Do not begin by training separate deep models for every symbol and timeframe. Start with one shared CatBoost model using symbol, timeframe, strategy, session, and direction as features. Split into specialized models only after each segment contains enough resolved candidates and walk-forward evidence shows a consistent improvement.

## 15. Definition of Success

The integration is successful when:

- Every candidate is reproducibly captured and labeled.
- Training and live inference use exactly the same feature definitions.
- Validation contains no future leakage.
- Predicted probabilities are calibrated.
- The model improves expected R after costs over the current engine and a simple baseline.
- Performance remains stable across time and key market segments.
- The engine can safely abstain, fall back, and roll back.
- Every live prediction can be traced to a model version, feature schema, and immutable candidate snapshot.

The central principle is simple: **train on the decision the engine actually makes and the payoff it actually realizes**. Price prediction is useful only when it improves that candidate-level outcome decision.
